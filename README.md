# 企业知识库 RAG 检索系统

把一批 PDF 技术文档做成**能溯源**的知识库问答系统：提问后检索出相关段落，回答时标注来源文件名与页码。

当前进度：**解析 / 切块 / 检索层已完成并实测**，向量检索与生成层开发中。

---

## 为什么做这个

大模型不知道你的私有文档。RAG（检索增强生成）的思路是：先从文档里检索出相关段落，再连同问题一起送给模型，让它基于这些内容回答——这样既能避免编造，也能标注出处。

**这个项目的重点不是"跑通一个 RAG demo"**，而是把两个真正卡人的环节做扎实：

1. **文档解析**：PDF 抽取出来的文本远没有想象中干净，段落边界、表格结构、阅读顺序都需要自己重建
2. **检索评测**：用真实失败案例证明「哪种方案在什么情况下不行」，而不是笼统地说"效果不错"

|---|---|---|---|

| 系统详细设计文档 | 86 | 73,528 | 9 |
| **合计** | **214** | **155,839** | **44** |

四份文档全部带文字层，无需 OCR。

### 切块策略对比

单份需求规格说明书，`size=500, overlap=60`：

| 策略 | 块数 | 中位长度 | <100 字块 | 跨页块 |
|---|---|---|---|---|
| fixed（固定长度硬切） | 133 | 249 | 13 | 14 |
| paragraph（段落装箱） | 160 | 203 | 33 | 7 |
| section（章节感知） | 164 | 200 | 32 | 8 |

**三种策略的差异是可测量的，而不是"感觉更好"**。固定长度切法会切断句子（"本文档不包含"→"档不包含"），段落装箱保留句子完整但会留下碎块。

### 检索性能

- 645 块索引，中文 bigram 切分，词表 **14,502** token
- 检索耗时 **0.2 – 1.0 ms**（top-3）
- 解析首次 25.4s；加缓存后 **0.003s**，加速 **4542×**

## 检索实测：8 条真实案例

详见 [`stage1/EVAL-CASES.md`](stage1/EVAL-CASES.md)。结论：**成功 3 / 部分正确 2 / 失败 1 / 待测 2**。

这个命中率是诚实数字，没有美化。

### 两条典型失败

**F1「系统支持哪些还款方式」** → top-1 命中「3.2 性能需求」（完全无关）

根因：「系统」「支持」是极高频词，BM25 的 IDF 压不住它们，带「支持」的性能需求表反而得分最高。真正含「还款方式」的是表格块，单元格切分削弱了 bigram 命中。

**F2「农户能贷多少钱」** → top-1 命中「联合贷款人推荐表」（只因为表里有「多少次」）

根因：**「贷多少钱」和文档里的「意向贷款金额」「申请额度」没有任何字面重叠**。这不是调参能修的，是纯关键词检索的物理上限。

### 这条失败案例的价值

它不是 bug，是**上向量检索的最强论据**。已用 embedding 实测验证：

```
query: 农户能贷多少钱
  vs 融资意向包含意向贷款金额字段，信贷产品含申请额度   → 0.5321  ✅
  vs 系统支持哪些还款方式                              → 0.4161  ❌

query: 系统支持哪些还款方式
  vs 还款方式为到期还本付息                            → 0.7332  ✅
  vs 并发用户数支持 100～300 个用户同时在线             → 0.4271  ❌
```

两条都排对了。**「关键词法无解、向量法有解」是实测结论，不是猜测。**

## 技术实现

```
PDF ──► 解析器 ──► 切块器 ──► BM25 索引 ──► 检索
        │            │            │
        │            │            └─ 中文 bigram + 停用词
        │            └─ fixed / paragraph / section 三策略
        └─ 行→段聚类、表格还原、页眉页脚剔除、阅读顺序重排
```

### 解析层：为什么不能用 pymupdf 的 blocks

实测这份 Word 导出的 PDF，`get_text("blocks")` 返回的 block **恰好等于一行**——第 48 页 10 个 block 是：页眉 + 页码 + 图注 + 标题 + 6 行正文。直接按 block 切，中位长度只有 **21 字**（"操作流程""硬件平台"）。

自实现的「行→段」聚类：

1. 按 y 坐标排序（**不能信任 PDF 返回顺序**）
2. 逐行计算与上一行的 gap
3. `gap > 字号 × 1.45` **或** `字号变化 > 1.2pt` → 断段
4. 段内把中文断行拼回去（"产\n品" → "产品"）

用字号而非固定像素阈值，换文档不用调参。

### 表格处理

表格用 `page.find_tables()` 抠出，转成 Markdown，**整块不切**——切了会得到半个表格，模型看不懂。宁可单块 1256 字超长，也不能破坏结构。

21 行 2 列的术语表，不打平是 `|专家|用户角色之一...|`；打平会变成 42 行孤立短句，语义完全断裂。

### 可溯源设计

块记录**跨页页码列表**而非单一页码。实测 500 字的块常横跨 2–3 页，只标一个页码等于说谎——用户翻过去找不到后半截内容，"可溯源"这个卖点当场破产。

来源渲染为「第 5-7 页」而不是「第 5 页」。

### 中文检索：bigram 而非分词库

`智能匹配` 整词入库则搜「匹配」命中不了；单字入库又太碎。滑动 bigram（`智能`/`能匹`/`匹配`）是成本最低的折中——不引入 jieba 依赖，不需要维护词典。

## 踩坑精选

完整记录见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)（共 23 条）。这里挑 5 条最有代表性的：

**1. 三种切块策略输出完全一致**
换三个参数跑出一模一样的 288 块 / 36136 字。第一反应不是"策略本就该一样"，而是实现有问题。查出来是累加缓冲区写在了循环体内，每段清零，跨段装箱完全没生效。修复过程中又引入两个新 bug（内容重复 + 截断），最终拆成 `buf` / `carry` / `buf_pages` 三个独立状态才对。

**2. 表格章节归属错了一整页**
ARIMA 表格被标成上一页的章节名。根因：表格在页面循环开头创建，此时章节指针还是上一页的值。修复：表格与正文塞进同一个按 y 排序的队列，章节指针沿 y 序自然推进。

> 来源标注错误比检索不到更严重——用户点开来源发现货不对板，整个"可溯源"卖点就没了。

**3. 拍脑袋的 0.5 阈值把正常数据判成异常**
embedding 相似度 0.352 被标为"偏低"。没有直接改阈值，而是写标定脚本做了四组对照（24 条文本），实测：等价 0.99 / 高度相关 0.75 / 弱相关 0.30 / 无关 0.22。那两句话属于"弱相关"，**0.35 完全正常**。

> 拍脑袋的阈值最坏的作用不是漏报，是在正常数据上误报，然后你开始怀疑一个本来没问题的系统。

**4. `load_dotenv(override=True)` 破坏环境变量优先级**
shell 里设的变量被 `.env` 文件反过来覆盖。它解决的是"改了配置立刻生效"这个不存在的问题（每次运行都是新进程），代价是破坏了 12-factor 的配置优先级约定，且 CI/CD 注入的变量会失效。

**5. 验证手段与被测对象必须同层**
写入 `.env` 后用 `importlib.reload` 回读验证，结果误报失败——reload 受 `override=False` 影响，读到的是进程内的旧空值。目标本是"文件内容对不对"，却去读"内存里的环境变量"。**想验什么就直接读什么。**

## 快速开始

```bash
# 1. 安装依赖
pip install fastapi uvicorn streamlit openai chromadb python-dotenv pymupdf

# 2. 配置
cp .env.example .env
# 编辑 .env，填入 DASHSCOPE_API_KEY（或改用 deepseek）

# 3. 环境自检
python stage0/check_env.py

# 4. 跑通全流程
python stage1/run_stage1.py -q "联合贷款人是怎么推荐的？权重怎么算"
```

输出示例：

```
问题：联合贷款人是怎么推荐的？权重怎么算
  3 条命中，检索耗时 0.2ms

  #1  score=19.680  系统详细设计文档.pdf 第 61 页  〔5.5 推荐算法〕
      命中词: 联合, 贷款, 推荐
      ...
```
