# 企业知识库 RAG 检索系统

把一批 PDF 技术文档做成**能溯源**的知识库问答系统：提问后检索出相关段落，回答时标注来源文件名与页码。

当前进度：**解析 / 切块 / 检索层已完成并实测**，向量检索与生成层开发中。

---

## 为什么做这个

大模型不知道你的私有文档。RAG（检索增强生成）的思路是：先从文档里检索出相关段落，再连同问题一起送给模型，让它基于这些内容回答——这样既能避免编造，也能标注出处。

**这个项目的重点不是"跑通一个 RAG demo"**，而是把两个真正卡人的环节做扎实：

1. **文档解析**：PDF 抽取出来的文本远没有想象中干净，段落边界、表格结构、阅读顺序都需要自己重建
2. **检索评测**：用真实失败案例证明「哪种方案在什么情况下不行」，而不是笼统地说"效果不错"

## 实测数据

### 语料

**Kubernetes 官方中文文档 63 篇**（© The Kubernetes Authors，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)）。

| 项 | 数值 |
|---|---|
| 文档 | 63 篇 / 54.9 万字 |
| 切块 | 1290 块（中位 444 字） |
| 来源 | [kubernetes/website](https://github.com/kubernetes/website) `content/zh-cn/docs` |

选这份语料的原因：许可证明确可分发、有官方中文翻译而非机翻、**事实密度高**
（参数名、默认值、组件职责都是可精确验证的内容）。

语料本体不入库，`python stage5/fetch_corpus.py` 可重新抓取；署名与来源清单已保留。

### 评测集：130 条

| 类型 | 数量 | 判定方式 |
|---|---|---|
| fact（事实题） | 120 | 回答包含标准答案关键词 |
| refuse（应拒答） | 10 | 必须拒答 |

**答案不是编的**：由 LLM 从原文出题，但每条答案都要通过**程序校验——必须逐字出现在原文 chunk 里**。
实测淘汰了 3 条「答案不在原文中」的幻觉。

### 检索层：5 组配置 × 120 条

| 配置 | Hit@1 | Hit@3 | Hit@5 | P50 延迟 |
|---|---|---|---|---|
| fixed / hybrid | 88 (73.3%) | 108 (90.0%) | 115 (95.8%) | 152ms |
| **paragraph / bm25** | **98 (81.7%)** | 111 (92.5%) | 114 (95.0%) | **2ms** |
| paragraph / hybrid | 95 (79.2%) | 110 (91.7%) | **116 (96.7%)** | 162ms |
| paragraph / vector | 84 (70.0%) | 107 (89.2%) | 109 (90.8%) | 146ms |
| section / hybrid | 98 (81.7%) | 111 (92.5%) | 115 (95.8%) | 153ms |

**结论：事实型问答上 BM25 的 Hit@1 最高，且快 80 倍。** 混合检索的优势在召回（Hit@5 最高）。

### 生成层：三种判定方式对照

| 判定方式 | 120 条原始 | 115 条（剔除缺陷题） |
|---|---|---|
| 严格字符串匹配 | 93 (77.5%) | 91 (79.1%) |
| **LLM 语义裁判** | 111 (92.5%) | **111 (96.5%)** |
| 拒答准确率 | 10/10 | 10/10 (100%) |

延迟 P50 2282ms / P95 ~6500ms。

**为什么有两个数**：字符串匹配零主观成分但会漏判同义改写
（标准答案「30 秒钟」vs 回答「30 秒」判为错）；
LLM 裁判能识别这类，但依赖模型质量。所以真实水平在
**79%–96% 之间，最合理估计是 96.5%**。

### 这个数字怎么验证的

**1. 人工复核失败案例** —— 27 条失败逐条看，发现 5 条是**题目本身有缺陷**
（文档有多个示例导致答案不唯一、标准答案与原文矛盾）。剔除后重算。

**2. 交叉验证裁判** —— 用 qwen-max 独立重判一遍：

| 指标 | 结果 |
|---|---|
| 两裁判一致率 | **116/120 (96.7%)** |
| 裁判 A 判对 | 111/120 |
| 裁判 B 判对 | 111/120 |

同一正确率 + 96.7% 一致率，说明结论稳定。**但两个裁判同属通义千问系列，
不完全独立**，严格验证需要异源模型——这个局限已写进报告。

### 切块策略对比（沿用）

单份文档，`size=500, overlap=60`：

| 策略 | 块数 | 中位长度 | <100 字块 |
|---|---|---|---|
| fixed（固定长度硬切） | 133 | 249 | 13 |
| paragraph（段落装箱） | 160 | 203 | 33 |
| section（章节感知） | 164 | 200 | 32 |

固定长度切法会切断句子；段落装箱保留句子完整但会留碎块。

## 检索实测：两种结论为什么不矛盾

阶段 3 用口语化 query 测（旧语料，10 条），结论是**向量明显更强**：

| query | BM25@3 | 向量@3 |
|---|---|---|
| 口语化组（「这个系统能装多少人同时用」） | 1/4 | **3/4** |

阶段 5 用事实型 query 测（130 条），结论是 **BM25 更强**（Hit@1 81.7% vs 70.0%）。

**两者不矛盾，是题型不同**：

- 口语化提问 → 与文档无字面重叠 → 向量有优势
- 事实型提问 → 含大量专有名词（`storageClassName`、`ephemeralcontainers`）→ BM25 是强信号

所以选型建议：**事实型问答用 BM25（快 80 倍），口语化场景用混合检索。**

### 一个量化过的失败案例

问「这个系统能装多少人同时用」（口语，与文档「并发用户数」零字面重叠）：

- **BM25** → 「根据现有资料无法确定」——检索失败，不是模型克制
- **混合** → 答出「100~300 并发」，引用两份互相印证的资料

**答案层面的差异比指标更直接。**

---
```
query: 一次请求要等多久（口语）
  vs 接口响应时间应控制在二百毫秒以内        → 命中 ✅
  vs 系统默认采用单线程顺序处理              → 未命中

query: 怎么让它快一点（口语）
  vs 批量写入比逐条写入高一个数量级          → 命中 ✅
```

10 条 query（5 条口语 + 5 条书面）中，向量检索命中 9 条，简化的字面重叠基线命中 7 条；
且字面基线在 3 条口语 query 上与所有候选**零重叠**，根本无从下手。

**必须说清局限**：该实验只有 5 条候选文档，难度远低于真实场景的 645 选 3，
命中率不能外推；字面基线也是简化的 bigram 重叠计数，不是真实的 BM25。
它的价值是**证明口语 query 确实存在语义鸿沟**，而非给出精确的优劣比。
正式对比放到阶段 5 的评测集里做。

**标定实验**（`stage0/calibrate_embedding.py`，24 条通用技术文本）：

| 语义关系 | 余弦相似度均值 |
|---|---|
| 完全等价（只差标点） | 0.994 |
| 高度相关（同主题不同表述） | 0.626 |
| 弱相关（同领域不同子话题） | 0.301 |
| 无关（不同领域） | 0.177 |

单调有序，等价组与无关组差 0.817。这个分布决定了检索阈值该定在哪里。
最初我拍脑袋把阈值定成 0.5，实测 0.35 触发误报 —— 标定之后才发现那两条文本
本来就属于「弱相关」，0.35 是正确的值。

## 技术实现

```
文档 ──► 解析器 ──► 切块器 ──► 索引 ──► 检索 ──► prompt ──► 回答+来源
          │           │          │        │
          │           │          │        └─ BM25 / 向量 / RRF 混合
          │           │          └─ BM25倒排 + Chroma向量
          │           └─ fixed / paragraph / section 三策略
          └─ PDF：行→段聚类、表格还原、页眉页脚剔除
             Markdown：按标题层级和空行切分（无页码，标为「第 N 节」而不是伪造页码）
```

### 解析层：PDF 和 Markdown 的两套逻辑

**PDF 是难的**。实测这份 Word 导出的 PDF，`get_text("blocks")` 返回的 block
**恰好等于一行**——一页 10 个 block 是：页眉 + 页码 + 图注 + 标题 + 6 行正文。
直接按 block 切，中位长度只有 **21 字**（"操作流程""硬件平台"）。

自实现的「行→段」聚类：

1. 按 y 坐标排序（**不能信任 PDF 返回顺序**）
2. 逐行计算与上一行的 gap
3. `gap > 字号 × 1.45` **或** `字号变化 > 1.2pt` → 断段
4. 段内把中文断行拼回去（"产\n品" → "产品"）

用字号而非固定像素阈值，换文档不用调参。

### 表格处理

表格用 `page.find_tables()` 抠出，转成 Markdown，**整块不切**——切了会得到半个表格，模型看不懂。宁可单块 1256 字超长，也不能破坏结构。

21 行 2 列的术语表，不打平是 `|专家|用户角色之一...|`；打平会变成 42 行孤立短句，语义完全断裂。

### 可溯源设计

块记录**跨页页码列表**而非单一页码。实测 500 字的块常横跨 2–3 页，只标一个页码等于说谎——用户翻过去找不到后半截内容，"可溯源"这个卖点当场破产。

来源渲染为「第 5-7 页」而不是「第 5 页」。

### 中文检索：bigram 而非分词库

`智能匹配` 整词入库则搜「匹配」命中不了；单字入库又太碎。滑动 bigram（`智能`/`能匹`/`匹配`）是成本最低的折中——不引入 jieba 依赖，不需要维护词典。

## 踩坑精选

完整记录见 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)（共 23 条）。这里挑 5 条最有代表性的：

**1. 三种切块策略输出完全一致**
换三个参数跑出一模一样的 288 块 / 36136 字。第一反应不是"策略本就该一样"，而是实现有问题。查出来是累加缓冲区写在了循环体内，每段清零，跨段装箱完全没生效。修复过程中又引入两个新 bug（内容重复 + 截断），最终拆成 `buf` / `carry` / `buf_pages` 三个独立状态才对。

**2. 表格章节归属错了一整页**
ARIMA 表格被标成上一页的章节名。根因：表格在页面循环开头创建，此时章节指针还是上一页的值。修复：表格与正文塞进同一个按 y 排序的队列，章节指针沿 y 序自然推进。

> 来源标注错误比检索不到更严重——用户点开来源发现货不对板，整个"可溯源"卖点就没了。

**3. 拍脑袋的 0.5 阈值把正常数据判成异常**
embedding 相似度 0.352 被标为"偏低"。没有直接改阈值，而是写标定脚本做了四组对照（24 条文本），实测：等价 0.99 / 高度相关 0.75 / 弱相关 0.30 / 无关 0.22。那两句话属于"弱相关"，**0.35 完全正常**。

> 拍脑袋的阈值最坏的作用不是漏报，是在正常数据上误报，然后你开始怀疑一个本来没问题的系统。

**4. `load_dotenv(override=True)` 破坏环境变量优先级**
shell 里设的变量被 `.env` 文件反过来覆盖。它解决的是"改了配置立刻生效"这个不存在的问题（每次运行都是新进程），代价是破坏了 12-factor 的配置优先级约定，且 CI/CD 注入的变量会失效。

**5. 验证手段与被测对象必须同层**
写入 `.env` 后用 `importlib.reload` 回读验证，结果误报失败——reload 受 `override=False` 影响，读到的是进程内的旧空值。目标本是"文件内容对不对"，却去读"内存里的环境变量"。**想验什么就直接读什么。**

## 快速开始

```bash
# 1. 安装依赖
pip install fastapi uvicorn streamlit openai chromadb python-dotenv pymupdf

# 2. 配置
cp .env.example .env
# 编辑 .env，填入 DASHSCOPE_API_KEY（或改用 deepseek）

# 3. 环境自检
python stage0/check_env.py

# 4. 拉取示例语料（Kubernetes 中文文档，约 55 万字）
python stage5/fetch_corpus.py

# 5. 建向量索引
python stage3/vector_index.py

# 6. 命令行问答
python stage1/run_stage1.py -q "Pod 的生命周期有哪几个阶段"

# 7. 起服务（两个终端）
python stage3/api.py
python -m streamlit run stage4/app.py
```

也可以把自己的 PDF / Markdown 放进 `data/docs/`（支持子目录），或用 `--docs` 指定目录。
两种格式都支持，解析器按扩展名自动分派。

输出示例：

```
问题：Pod 的生命周期有哪几个阶段
  3 条命中，检索耗时 0.2ms

  #1  score=12.345  pod-lifecycle.md 第 2 节  〔Pod 生命期〕
      命中词: Pod, 生命, 周期
```

来源会带上**定位信息**：PDF 显示「第 N 页」，Markdown 显示「第 N 节」。
没有页码的文档不伪造页码——那会破坏「可溯源」这个核心卖点。

## 已知不足

诚实说明，避免过度包装：

- **两个裁判同属通义千问系列**，交叉验证只能说明「同族模型下结论稳定」，
  严格验证需要异源模型（GPT / Claude）
- **评测集由 LLM 从原文生成**，比真实用户提问更贴近原文，会低估向量检索
- 剔除的 5 道缺陷题由人工判定（文档含多个示例导致答案不唯一），
  编号与理由写在 `stage5/final_score.py` 里，可逐条复核
- 换切块策略后 chunk_id 变化，fixed/section 的 Hit@k 是近似值
- 拒绝类样本只有 10 条，统计意义弱；否定式、多跳推理题尚未覆盖
- 单机单线程，没有并发与性能测试
- 混合检索两路是串行的，并行可把延迟从 sum 降到 max
- **线上部署在免费 CPU 档**，冷启动与高并发未做压测
